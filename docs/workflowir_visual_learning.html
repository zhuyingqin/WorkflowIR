WorkflowIR 学习地图

把 tool-using LLM agent 从 prompt engineering 推向 compiler engineering。

Paper Storyline

让 Agent Workflow 进入可编译时代

ReAct 让 LLM 能灵活调用工具，但容易局部短视；DAG planner 提供全局结构，但仍然执行未验证的图。 WorkflowIR 的核心是把工具工作流表示成 typed intermediate representation，让计划在执行前被检查、优化，并在执行中被局部修复。

三代 Agent 对比

我们的论文不是“再做一个 planner”，而是指出 planner 生成的图也需要像程序一样被验证和修复。

ReAct

每一步根据 observation 决定下一个 action，灵活但缺少全局结构。

  • 容易局部贪心和绕圈。
  • 长链任务中错误持续累积。
  • 每一步都调用 LLM，成本高。

DAG Planner

先生成全局工具计划，再交给 executor 执行，结构更清晰。

  • DAG 通常只是“看起来合理”。
  • 缺少类型、schema 和前置条件检查。
  • 失败后常常整体重试或重规划。

WorkflowIR

把 workflow 表示成可编译程序，并在执行前后持续约束。

  • 执行前发现确定性错误。
  • 在图层面优化成本和并行度。
  • 执行失败后做最小子图修复。

具体例子

同一个旅行预算任务，在 ReAct、普通 DAG 和 WorkflowIR 下会呈现完全不同的可靠性。

用户任务

帮我找下个月去东京开会的机票、酒店，并生成预算表。

关键隐含约束：出发城市、会议地址、日期范围、币种、预算表字段、API 可用性。

Thought: 先搜索机票。
Action: search_flight(destination="Tokyo")
Observation: missing origin and date

Thought: 用户说下个月，先猜一个日期范围。
Action: search_flight(destination="Tokyo", date="next month")
Observation: multiple ambiguous ranges

Thought: 先查酒店。
Action: search_hotel(city="Tokyo")
Observation: too many results

风险：中途忘记会议地址，重复查酒店，预算表字段不一致。
search_flight
  -> search_hotel
  -> calculate_budget
  -> write_report

问题：
- search_flight 是否需要出发城市？
- search_hotel 是否需要会议地址？
- calculate_budget 是否需要统一币种？
- write_report 是否需要固定表格 schema？
- search_flight 和 search_hotel 是否其实可以并行？

A. infer_travel_constraints

抽取出发地、日期范围、会议地点和预算偏好。

output: TravelSpec

B. search_flights

基于 TravelSpec 搜索航班。

input: TravelSpec
output: list[FlightOption]

C. search_hotels

基于地点和日期搜索酒店。

input: TravelSpec, Location
output: list[HotelOption]

D. normalize_currency

统一机票和酒店价格币种。

input: FlightOption[], HotelOption[]
output: BudgetTable

E. write_report

生成预算表和 Markdown 报告。

input: BudgetTable
output: MarkdownReport 
Type Check:
  B.input == TravelSpec
  C.input includes Location
  D.input prices have currency fields

Dataflow Check:
  A -> B, A -> C
  B,C -> D
  D -> E

Cost Optimization:
  B and C can run in parallel
  cache duplicated city/date queries

Repair Example:
  hotel API fails: missing meeting_address
  patch: add node infer_meeting_location
  add edge infer_meeting_location -> search_hotels

Compiler Passes

WorkflowIR 的论文贡献可以被组织成一组明确的编译器式 pass，每个 pass 都对应可测量的错误类型。

Type Check检查工具输入输出类型是否能连接，减少 type mismatch。
Dataflow Check确认每个参数都有上游来源，减少 missing dependency。
Precondition Check检查登录、日期、地点、权限等前置条件。
Cost Check预算、token、工具费用和 latency 的约束验证。
Optimization删除无用节点、合并重复调用、识别并行分支。
Repair把执行失败转为 counterexample，并局部 patch 子图。
关键论点：我们不是等 agent 失败后写一段 reflection，而是在执行前阻止确定性错误，并在执行中把失败精确映射到 WorkflowIR 的节点、边和参数。

如何做编译器检查

实现上需要三个对象：工具契约、WorkflowIR 图、诊断报告。检查器不是再问一次 LLM，而是用确定性规则先过滤明显不可执行的计划。

1. 给每个工具写 Contract

Contract 是检查器的类型系统。它可以来自 API schema、工具文档，也可以从历史成功/失败轨迹中学习。

ToolContract:
  name: search_hotels
  input:
    city: string
    check_in: date
    check_out: date
    location_hint: string?
  output:
    hotels: list[HotelOption]
  precondition:
    check_in < check_out
    city is not empty
  effects:
    provides: hotels.price, hotels.currency
  failure_modes:
    MissingDate
    AmbiguousLocation
    NoAvailability

2. 按顺序跑 Check Passes

每个 pass 输入一张 WorkflowIR 图，输出一组 errors / warnings / optimization hints。

A
Graph Check确认无环、入口/出口存在、所有节点可达。
B
Schema Check检查每个工具调用是否满足 required arguments。
C
Type/Dataflow Check检查上游输出类型能否喂给下游输入。
D
Precondition Check用已知变量验证日期、权限、登录、预算等条件。
E
Cost/Safety Check估计 token、工具费用、latency 和风险等级。
F
Patch Suggestion把错误定位到节点/边/参数，并生成最小修复建议。

3. 输出可执行诊断报告

报告必须能告诉 executor 或 repair model：哪里错、为什么错、最小怎么改。

MissingInput Node C `search_hotels` requires `location_hint`, but no upstream node produces it.
CurrencyMismatch Node D receives USD flight prices and JPY hotel prices. Insert `normalize_currency` before budget calculation.
Parallelizable Node B `search_flights` and Node C `search_hotels` only depend on TravelSpec, so they can run concurrently.
检查规则 检测方法 发现的问题 修复动作
Required input rule 对照 tool contract 的 required fields 缺少 `origin_city`、`check_in_date` 等参数 插入信息抽取节点，或向用户澄清
Type compatibility rule 检查上游 output type 是否能匹配下游 input type `list[HotelOption]` 被直接传给需要 `BudgetTable` 的节点 插入 transform / aggregation 节点
Precondition rule 执行符号规则或轻量验证函数 `check_in >= check_out`、未登录、权限不足 重排节点、补认证步骤、修正日期范围
Dependency rule 做图可达性和数据依赖分析 节点依赖不存在、死节点、错误顺序 补边、删死节点、重新拓扑排序
Cost rule 累加每个节点的 token、API cost、latency 估计 计划超预算、昂贵工具过早调用 便宜工具优先、并行化、缓存复用 
Compiler-style verifier pseudo-code:

def verify(workflow, tool_contracts, budget):
    diagnostics = []
    diagnostics += check_graph_is_dag(workflow)
    diagnostics += check_required_inputs(workflow, tool_contracts)
    diagnostics += check_type_and_dataflow(workflow, tool_contracts)
    diagnostics += check_preconditions(workflow, tool_contracts)
    diagnostics += check_cost_and_safety(workflow, budget)

    if has_blocking_errors(diagnostics):
        patch = propose_minimal_patch(workflow, diagnostics)
        return VerificationResult(status="blocked", diagnostics=diagnostics, patch=patch)

    optimized = optimize_workflow(workflow)
    return VerificationResult(status="ready", diagnostics=diagnostics, workflow=optimized)

实验故事

实验要分成“可控诊断”和“真实 benchmark”两条线：前者证明编译器检查确实减少哪类错误，后者证明方法能迁移到已有 tool-use agent 任务。

实验 Benchmark Stack

这张 AI 生成图展示四层实验栈：可控 sandbox、DAG planning benchmark、真实 API 风格 tool-use benchmark，以及交互式/学术查询类任务。网页下方的文字表格给出准确实验设计。

第一层：Controlled Sandbox

我们自建 30-50 个多工具任务，每个工具都有 schema、precondition、effect 和 failure mode，用于精确注入错误并做错误归因。

第二层：Planning Benchmark

用 ComplexTool-Plan 评估 planner 生成 DAG / WorkflowIR 的结构质量，重点看 node selection、edge dependency 和 exact match。

第三层：Execution Benchmark

用 StableToolBench / ToolBench、ScienceWorld、ToolQuery-Academic 测真实执行效果、工具调用稳定性和成本。

Controlled Workflow Sandbox

这是我们自己构造的最小可控环境，目的不是追求大规模，而是把错误类型拆清楚。

  • 特点工具 contract 完整、gold workflow 已知、可控注入缺参/错参/错序/工具失败。
  • 测什么静态检查能否提前发现错误，repair 能否最小 patch。
  • 指标invalid call rate、repair success、error localization accuracy、cost reduction。

ComplexTool-Plan

`Beyond ReAct` 提出的 DAG planning 数据集，来自 4,500+ API 工具库，区分 Easy/Hard 难度。

  • 特点有 ground-truth DAG，可直接评估工具节点选择和依赖边建模。
  • 测什么WorkflowIR planner 是否比普通 DAG planner 更容易生成可检查结构。
  • 指标node precision/recall/F1、edge precision/recall/F1、DAG exact match。

StableToolBench / ToolBench

ToolBench 覆盖大量真实 API 风格工具；StableToolBench 用缓存和 API simulator 缓解真实 API 不稳定问题。

  • 特点任务按工具泛化和场景复杂度划分，包含 seen/unseen tools 与 multi-tool cases。
  • 测什么WorkflowIR 是否提升端到端成功率，同时减少无效工具调用和推理轮数。
  • 指标Solvable Pass Rate、Solvable Win Rate、inference steps、tool calls、token cost。

ScienceWorld / ToolQuery-Academic

ScienceWorld 是交互式科学任务环境；ToolQuery-Academic 更接近学术 API 查询与工具选择场景。

  • 特点ScienceWorld 强调多步交互和状态变化；ToolQuery-Academic 强调工具选择和参数传递。
  • 测什么WorkflowIR 在动态状态任务和学术查询 workflow 中是否仍然有效。
  • 指标task success、action efficiency、state/precondition errors、tool-selection accuracy。

最终卖点

论文定位不是“又一个 agent 框架”，而是提出一个更基础的系统抽象。

英文 Claim

ReAct agents are locally adaptive but globally myopic and expensive. Planner-based agents improve global structure but still execute unverified workflow graphs. We introduce a compiler-style architecture that represents tool workflows as typed IR, enabling static validation, cost-aware optimization, and counterexample-guided repair.

中文 Claim

ReAct 解决了工具调用的灵活性，但没有解决全局结构；DAG planner 解决了全局结构，但没有解决可验证执行。 我们提出 WorkflowIR，把 agent workflow 从“模型生成的计划”提升为“可编译的程序”。

更可靠

执行前发现类型、依赖、前置条件和预算错误。

更便宜

减少无效 LLM/tool calls，合并重复步骤，识别可并行分支。

更可修复

失败后局部 patch 子图，而不是整条 workflow 重来。
